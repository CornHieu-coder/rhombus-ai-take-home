# Run the UI tests

The take-home requires command-line automation of **S3 → AI Builder → GCS → scheduling**, with no fixed sleeps and assertions on real outcomes. This guide covers login, existing-project checks and the full setup test. The [recorded live result](../observations/ui-journey.md) shows what passed and what remains unverified.

<a id="journey-prerequisites-and-isolation"></a>

## Prerequisites

Run commands from the repository root. Use Node.js 20+ and install the dependencies and browser:

```bash
npm ci
npx playwright install chromium
```

Copy `.env.example` to ignored `.env` and fill in:

- `RHOMBUS_PROJECT_NAME`: your original Rhombus project's exact name. Replace the example **Rhombus QA Take Home**, which identifies the original scheduler-evidence project. The full setup test uses a separate project named **Rhombus QA Playwright Journey**, which must have no enabled schedules before starting.
- `RHOMBUS_S3_BUCKET`, `RHOMBUS_S3_REGION` and `RHOMBUS_S3_PREFIX`: the existing S3 source. Its object key is the prefix plus `baseline.csv`; include a trailing slash in a nonempty prefix. Prepare it using [datasets/baseline.csv](../datasets/baseline.csv). The test selects the object without uploading or overwriting it.
- S3 access: apply the [read policy generated by Rhombus](https://doc.rhombusai.com/docs/Integrations/aws-s3-connection/) before running. The test can reuse an available connection or connect the bucket through the UI.
- `RHOMBUS_GCS_BUCKET`: the output bucket. When the separate project needs a new destination, set `RHOMBUS_GCS_SERVICE_ACCOUNT_JSON_PATH` to an ignored local [service-account JSON key](https://doc.rhombusai.com/docs/Integrations/gcp-storage-connection/) with the required bucket access. An existing destination can be reused.

Save a Rhombus login using the next section. Keep login files and keys outside public evidence.

## Save a session

Run the login helper, sign in to Rhombus in the browser it opens, then follow its prompt to save your login:

```bash
node ui-tests/save-auth.mjs
```

The helper saves only Rhombus login data under ignored `auth/`, excluding Google browser data. If Google rejects sign-in in this browser, use the [normal Chrome alternative](#use-normal-chrome-to-save-your-login) at the end of this guide. That alternative was verified on 2 October 2026.

## Existing-project checks

To inspect the project already named in `.env`, run:

```bash
npm run test:ui
```

These checks inspect the saved S3, cleaning and GCS nodes and their connections. The UI and authenticated API schedule checks require `next_run_at` to be a valid timestamp after the observation time; the UI also checks the **Next run** display. A parseable old timestamp fails.

For history checks, set `RHOMBUS_SCHEDULE_HISTORY_SINCE` to the start of your current observation window as an ISO timestamp with a timezone, before allowing an automatic attempt. Then set `RHOMBUS_EXPECT_SCHEDULE_HISTORY=1`. For example, in PowerShell:

```powershell
$env:RHOMBUS_SCHEDULE_HISTORY_SINCE = (Get-Date).ToUniversalTime().ToString('o')
# Allow an automatic attempt after this timestamp before running the checks.
$env:RHOMBUS_EXPECT_SCHEDULE_HISTORY = '1'
npm run test:ui
npm run test:api
```

Use your actual observation window; do not reuse a timestamp from historical evidence. When history checks are enabled, a missing, invalid or future window start fails the prerequisite. A qualifying record must identify the selected project and schedule, report `trigger=scheduled` or `trigger=schedule`, and have `started_at` between the window start and the observation time, inclusive. The UI additionally requires a matching execution ID in its history table.

History presence establishes an automatic attempt in that window. The attempt may be unfinished or failed; this check does not establish successful completion or a GCS export. The [additional automatic-delivery check](#strict-delivery-mode) verifies those outcomes separately.

The schedule checks need an enabled schedule; they select the first enabled one. Original schedule **209** was paused in the latest capture. A missing enabled schedule is a prerequisite problem, and a skipped history check is not a pass. These checks do not rebuild the pipeline or validate a GCS file. The [scheduler report](../observations/scheduler-support-report.md) documents the earlier enabled-schedule observation windows.

## Run the S3 → AI Builder → GCS → schedule test

The [Playwright test](pipeline-journey.spec.ts) changes its separate test project, so it runs only when explicitly enabled. In PowerShell:

```powershell
$env:RHOMBUS_RUN_PROVISIONING_JOURNEY = '1'
$env:RHOMBUS_JOURNEY_VERIFY_DELIVERY = '0'
npm run test:journey -- --workers=1
Remove-Item Env:RHOMBUS_RUN_PROVISIONING_JOURNEY
Remove-Item Env:RHOMBUS_JOURNEY_VERIFY_DELIVERY
```

Use one worker. The test:

1. Opens or creates the separate project and records the original project's schedule states.
2. Selects the connected S3 baseline and checks its listing, saved selection and preview.
3. Submits a new AI Builder request and checks the three connected nodes and saved cleaning prompt. If Python code is missing, it submits Rhombus's **Regenerate With Feedback** form. No Python is edited manually.
4. Selects or creates the GCS destination, saves CSV export settings and checks them after reload.
5. Creates an enabled every-minute schedule, checks its saved pipeline and opens its history. Cleanup pauses that exact schedule and checks that the original project's schedule states were preserved.

The test waits for responses and saved results using bounded polling; it uses no fixed sleeps. Cleanup failures are reported. If the enable flag is set in `.env`, the command alone is sufficient:

```bash
npm run test:journey -- --workers=1
```

## What a pass proves

| Command | What a pass establishes |
| --- | --- |
| `npm run test:ui` | The existing pipeline has the expected connections and the enabled schedule reports a future next run. Enabled history checks correlate an automatic attempt within the explicit window with a visible execution ID. A skipped check provides no result. |
| `npm run test:journey -- --workers=1` | S3 selection, AI-generated pipeline/code, GCS CSV settings and a new enabled schedule were saved and verified through the live application. |

The full setup test passed live on **3 October 2026: 1 passed (1.4m)**. It used project **5252**, destination **58** and schedule **215**. See the [five-step report and evidence](../observations/ui-journey.md).

## Important limits

The default full setup test pauses its schedule during cleanup. Its pass does not establish that the schedule later ran or delivered a new file. The recorded run did not independently download the current S3 bytes or validate a new GCS export.

Saved code and connected nodes also do not certify every cleaning rule. The [run report](../observations/ui-journey.md#limits) records the generated code's empty-ID gap and an output error shown before GCS setup. Real-byte cleaning and repeated-output evidence comes from the [original manual baseline controls](../observations/baseline-manual.md).

The required successful automatic baseline remains unverified. The [canonical scheduler report](../observations/scheduler-support-report.md) contains the controlled observation windows and the effect on scheduled drift testing.

## Additional automatic-delivery check

We added an optional check that waits for a new scheduled execution, finds the new GCS file from that run and validates its downloaded contents. This is our implementation choice for checking the scheduled result, not a separate take-home requirement. **The complete check remains unverified live** because the authenticated cloud browser was unavailable in the recorded session.

When enabled, it first downloads the actual S3 object and requires its bytes to match the repository baseline. A pass also requires a newly completed execution for the created schedule, completion of every expected node, one new GCS object with this run's filename and creation time, and passing CSV validation. Old or manual runs cannot satisfy these checks.

It observes the schedule until its next-run time plus 180 seconds by default. No verified delivery within a completed observation window is recorded as blocked. Cloud access problems, failed requests or other observation errors do not establish a scheduler defect. Browser prerequisites and commands are in the [advanced section](#run-the-additional-delivery-check).

## Advanced setup and troubleshooting

### Use normal Chrome to save your login

If Google rejects the helper's browser, sign in yourself using a dedicated Chrome profile. On Windows, open this command from Run (Win+R), adjusting the Chrome path if needed:

```text
"C:\Program Files\Google\Chrome\Application\chrome.exe" --user-data-dir="%LOCALAPPDATA%\RhombusTakeHome\Chrome" --remote-debugging-address=127.0.0.1 --remote-debugging-port=9333 --new-window https://rhombusai.com
```

After signing in and opening Rhombus, save the login:

```bash
node ui-tests/save-auth.mjs --cdp
```

Here `--cdp` lets the helper connect to the Chrome window already open on your computer. `RHOMBUS_CDP_URL` can override the login helper's connection address. See [Google sign-in guidance](https://support.google.com/accounts/answer/7675428?hl=en) and [Chrome's dedicated-profile requirement](https://developer.chrome.com/blog/remote-debugging-port).

### Run the additional delivery check

Keep the dedicated Chrome open and sign in to the S3 and GCS consoles. Open the source and output bucket tabs before running; the check uses those existing tabs to list and download objects. It does not upload or delete cloud objects. Python 3.10+ is needed for local CSV validation.

On a shell supporting command-local environment variables:

```bash
RHOMBUS_RUN_PROVISIONING_JOURNEY=1 RHOMBUS_JOURNEY_VERIFY_DELIVERY=1 npm run test:journey -- --workers=1
```

In PowerShell, use the main example with `RHOMBUS_JOURNEY_VERIFY_DELIVERY = '1'`. The setup-only equivalent for other shells is:

```bash
RHOMBUS_RUN_PROVISIONING_JOURNEY=1 npm run test:journey -- --workers=1
```

Optional settings:

- `RHOMBUS_JOURNEY_PROJECT_NAME` changes the separate project name; it must differ from `RHOMBUS_PROJECT_NAME`.
- `RHOMBUS_CLOUD_CDP_URL` selects the cloud browser connection, defaulting to `http://127.0.0.1:9333`. It requires a loopback address on port 9333 and is separate from the login helper's address.
- `RHOMBUS_JOURNEY_GRACE_SECONDS` changes the observation time after the next-run boundary: default 180 seconds, allowed 60–600.
- `RHOMBUS_PYTHON` selects a Python executable. CSV validation uses Python's standard library.
- `RHOMBUS_JOURNEY_EVIDENCE_DIR` selects another local output directory.

The logic for rejecting old or unrelated executions and files, stale next-run timestamps and history records outside the explicit window can be checked without live access:

```bash
npm run test:journey-results
```

The original nine local delivery-result tests passed. Eight additional regressions cover next-run freshness, explicit history prerequisites and correlated automatic attempts; all 17 current local tests pass. They check our test logic without exercising Rhombus's scheduler or cloud delivery.

### Evidence files and publication

Local output defaults to `test-results/<test>/journey/`. It includes a manifest, step results, selected saved settings, masked screenshots and the Builder prompt/code. With the additional delivery check, it can also include verified input/output CSVs and validation reports. Later invocations may replace local results, so preserve any run you need before rerunning.

Automatic traces and failure screenshots are disabled for the full journey because destination setup can enter a private key. Controlled screenshots mask bucket names and visible emails; selected JSON/text evidence redacts credentials and signed URL queries. Existing-project tests can still write raw diagnostics under ignored `test-results/` and `playwright-report/`.

Review artifacts before copying them to `observations/evidence/ui-journey/<run-id>/` and linking the result from `observations/ui-journey.md`. Keep login files, keys, raw network captures and traces private. The [repository evidence section](../README.md#results-and-evidence-storage) records the submission's evidence status.
